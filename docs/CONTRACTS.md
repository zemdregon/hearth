# Hearth implementation contract

Daily questions use one configured couple. `FAMILY_QUESTION_PAIR` is optional JSON `[memberId, memberId]` or `null`; omission infers a pair only for a two-member household. Bootstrap/export include `questionPair`. New answers must send that expected pair as `participantIds`; the server verifies and stores it. An answer's date, question, and participants are immutable. Legacy answers without participants remain author-only. A nonauthor receives an answer only after both original participants answer the same question/day while that pair is still configured; the partner can then see it, and other family members can see it only with explicit `shareToProfile` consent. Config changes never reassign saved audiences. Same-day conflicts with earlier scopes reject new answers; all records are preserved. Demo visibility and mutations follow the same rules.

React/TypeScript/Vite client, Hono Cloudflare Worker with D1 and Workers AI. Single private family per deployment. Shared types in `src/shared/types.ts` describe implemented interfaces. No public registration or production seed data. Authentication uses internal, invite-only passkeys, with no passwords, email addresses, phone identities, OTP or social-login fallback. See [the authentication contract](AUTHENTICATION.md) for enrollment, recovery, sessions and verification gates. The Worker validates WebAuthn ceremonies and D1-backed sessions; Access JWT/email headers and development identity headers grant no access. The public auth routes permit only bounded ceremonies; invitations authorize registration, never direct sign-in.

API (JSON; errors `{error: string}`): GET `/api/bootstrap` returns Bootstrap. POST `/api/records` body `{kind, data}` returns FamilyRecord, server assigns owner/id. PATCH `/api/records/:id` body `{data, version}` returns updated FamilyRecord; optimistic version conflict 409. DELETE `/api/records/:id` uses body `{version}`, returns `{ok:true}`. PATCH `/api/modules/:id` body `{enabled:boolean}` returns ModuleConfig (admin only). POST `/api/recipes/import` body RecipeImportRequest returns RecipeImportResponse (draft only). GET `/api/export` returns versioned export. All /api responses no-store; origin-check all mutations. Authenticated records only; private moods and all answer visibility rules enforced on server; profile/mood/answer owner-only mutations; habit logs only habit owner. Disabled modules preserved, read and write access disabled. Dates YYYY-MM-DD in family timezone.

Bootstrap/export include a coarse whole-family `capacity` bucket: `available`, `near-limit` at 80% of either storage ceiling, or `full` at either ceiling (8,388,608 serialized data bytes or 10,000 records). It is read in the same D1 batch as records and module visibility, includes private and disabled-module records, and exposes no counts, byte totals, owners or module breakdowns. All authenticated members receive this intentionally shared operational signal; record visibility is unchanged. Capacity is guidance at the last successful refresh, not a reservation or guarantee a write will fit; atomic SQL triggers remain authoritative. The client treats a missing bucket as unavailable and clears stale guidance after confirmed record mutations until refresh succeeds. Demo guidance counts UTF-8 serialized data before filtering visibility. Pausing modules and exporting do not free storage; exports still include only the exporting member's visible enabled-module records.

`GET /api/bootstrap` returns a weak `ETag` derived from SHA-256 of the exact member-visible Bootstrap JSON. Every request still authenticates, checks configuration and rate limits, and reads a fresh visibility-filtered snapshot. A matching `If-None-Match` returns bodyless `304`; otherwise it returns complete JSON `200`. Both remain `no-store, private`. Hidden-record activity does not change the validator unless it changes the intentionally shared capacity bucket or another visible field. Export is always complete visible JSON, never conditional. The client explicitly bypasses HTTP caches and holds the validator only in provider memory alongside its complete snapshot. Confirmed mutations, identity/session clearing, demo transitions and unmount invalidate it. Accepted `304` responses preserve records identity but still advance render-driven family dates. An unexpected/mismatched `304` retries once without a validator; stale responses cannot restore a cleared session. No private responses or validators belong in service-worker caches, localStorage or IndexedDB. Conditional transfer does not reduce the full D1 read or raise storage limits.

Client store owned by root in `src/client/store.tsx`: `useFamily()` exposes `{ user, members, modules, records, timezone, demo, loading, error, addRecord(kind,data), updateRecord(record,data), deleteRecord(record), setModule(id,enabled), refresh(), enterDemo(), leaveDemo() }`. Mutations async, update state after successful server result, throw on error. `useRecords(kind)` returns typed records. UI module component exports `Recipes`, `Tasks`, `Notes`, `Streaks`, `Events`, `Moods`, `Questions`, `Profiles`, `Goals`, each zero-prop and imports store hooks. `src/client/components/ui.tsx` supplied by shell agent exposes `Button`, `Field`, `EmptyState`, `Modal`, `SectionHeader`, `Badge`; use basic HTML if necessary until available. Shell uses `src/client/App.tsx`, `main.tsx`, `styles.css`. Modules should have their own css files only if needed and use shared CSS classes `.card`, `.button`, `.button.secondary`, `.input`, `.field`, `.stack`, `.muted`, `.eyebrow`, `.pill`, `.grid-2`, `.grid-3`. Design: warm ivory, forest green, terracotta, serif headings, clean sans body; generous whitespace, accessible contrast, mobile-first. No external image/font dependencies.

Appearance follows the device color scheme by default, with explicit light/dark overrides stored under `hearth-theme` in localStorage. This public device preference contains no member identity or family content and survives sign-out. Selecting System removes the override; open tabs follow changes. A public script applies the preference before the app renders, and a blocked storage API leaves the control usable in memory. Recipe print sheets remain light; images are never globally inverted.

Inventory foundation is a pure domain library in `src/shared/inventory`, not yet an enabled module, API, storage schema or recipe adapter. It parses bounded quantity text into exact BigInt rational intervals, resolves explicit measurement conventions, scales and aggregates recipe demand, and returns `sufficient`, `insufficient` or `unknown`. Fractions remain exact through comparison; any integer storage projection rounds interval bounds outward. BigInts are not a JSON wire format. The arithmetic input/precision limits are separate from future per-lot persistence limits and invalid/over-budget calculations throw `RangeError`; callers must not turn errors into stock verdicts.

The evaluator requires reviewed exact item/form mappings and a complete eligible inventory snapshot. Forms must distinguish density-relevant preparation, packing and size. Optional/excluded lines and lots are explicit; an unquantified required ingredient prevents sufficiency, while a proven shortage on another ingredient still wins. Semantic count units are distinct, unresolved package sizes/bases have no automatic conversion, and ambiguous household measures require a confirmed profile. Cross-dimension conversion requires a single applicable, explicitly accepted calibration; reference/AI output alone does not establish acceptance. Future routes must validate persisted acceptance, ownership, module state, numeric storage limits and snapshot completeness on the server. Expiry, reservations, package parsing, free-text identity matching, persistence and consumption are not implemented by this library. `npm run test:inventory:d1` exercises only the proposed transaction primitives in a disposable local fixture.

Retroactive habit streaks: `POST /api/habits` takes `{ data: Habit, startDate? }` (strict; the habit's `userId` must be the caller). With a `startDate` it creates the habit plus an ordinary `habitLog` for every day from `startDate` through **yesterday** in the family timezone, in one atomic D1 batch (`createHabitWithHistory`): a disabled module, the storage budget or any constraint failure rolls back the habit too. Today is never backfilled so an unfinished day cannot count. The start must be a valid date before today and at most 366 days back (`backfillDates`/`MAX_BACKFILL_DAYS` in `src/shared/calendar.ts`, shared by client preview and server). Backfilled days are indistinguishable from manual check-ins (same bytes, owner and budget accounting), so the owner can uncheck any of them and deleting the habit removes them. Without `startDate` the route equals `POST /api/records` for habits, which remains available. Backfilling an existing habit is not supported; individual past days can still be toggled in the calendar.

Inventory storage and API (Stage 1) is household-shared and opt-in: module id `inventory`, migration `0008` adds its `modules` row **disabled**, and every `/api/inventory/*` route returns 403 while the row is disabled or missing (unlike original modules, a missing row means off; `moduleSettings` reports it disabled). Dedicated tables `inv_items`, `inv_locations`, `inv_lots`, `inv_txns`, `inv_ledger`, `inv_storage` and `inv_assert` (migration `0007`) are outside `records` and `family_storage`; inventory is not part of `/api/bootstrap`. Routes: `GET /api/inventory` (weak ETag/304), `GET /api/inventory/ledger?before&limit`, `POST /items`, `PATCH /items/:id`, `POST /items/:id/archive`, `POST /locations`, `POST /locations/:id/archive`, `POST /lots`, `POST /lots/:id/adjust` (`mode: add|remove|set`) and `POST /lots/:id/archive`. Items and lots are archived, never deleted; an item or location with live lots cannot be archived. Any active member may read and write (history is visible to everyone). `inv_txns.member_id` references `auth_members`, so inventory actors need no extra restore-roster coverage; module toggling stays administrator-only.

Wire quantities are integers in **ng** (mass), **nL** (volume) or whole counts of one named unit (`count:egg`…), at most 9×10^15. Every pound, ounce, gram and millilitre is exact; some US-customary volumes (a cup is 236,588,236.5 nL, a teaspoon is not a finite decimal) round to the nearest base unit, so consumers must treat a lot's supply as `[qty − ½, qty + ½]` base units (widened by `estBp` basis points for `estimated` lots), never as sub-unit exact. `stockQuantity` (`src/shared/inventory/stock.ts`) is the single parse/convert/validate path for client and server; the server never trusts client-converted numbers. Ranges, zero (except a recount), unit/dimension mismatch, unresolved cup/spoon conventions and ambiguous `oz` are rejected, not guessed. Every write carries a client `txnId` (8–100 chars) bound to the actor and a canonical request hash: an identical authorized retry replays the stored result (`200`, `replayed: true`, the affected lots' *current* state) before any state-dependent validation, anything else reusing the id is `409`. Writes are one atomic D1 batch (transaction header, assertion row, mutation, ledger row), guarded by module state, optimistic `version` and expected quantity; `inv_txns` and `inv_ledger` are append-only (triggers `INVENTORY_LEDGER_IMMUTABLE`) and capped (`INVENTORY_LIMIT`: 50 locations, 1,000 items, 2,000 active lots; `INVENTORY_LEDGER_FULL` at 100,000 ledger rows, with 1,000 rows of headroom reserved for archiving so stock can still be retired). Removal beyond recorded stock is refused (clamp-with-shortfall belongs to confirmed consumption, not yet built). Exports include an `inventory` section (state plus the newest 1,000 ledger entries, `schemaVersion` 2) only while the module is enabled; pausing preserves all rows. The availability engine is **not yet connected** to these tables: no recipe adapter, aliases, calibrations, reservations or consumption exist.
